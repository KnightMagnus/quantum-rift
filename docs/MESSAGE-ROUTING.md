# Message routing

## Routing boundary

`server/game-message-handlers.ts` defines the fixed action table.
`Game.createMessageHandlers` constructs it with an explicit, frozen capability facade:
live getters for services/state and forwarding calls retaining the core method
receiver. No whole `Game` object is passed to the action module.

Keep these responsibilities distinct:

- `Game.onMessage`: authentication, flood limiting, economic-freeze and activity
  gates, in their existing order.
- `createGameMessageHandlers`: 57 named actions, field validation/coercion and
  calls to their owners. The `portrait` action accepts only selectable catalog IDs
  and changes only the authenticated captain's saved portrait.
- `createMessageRegistry`: duplicate detection, fixed route listing, dispatch
  and ignored unknown/inherited names.

The switchboard connects multiple services, and some inline actions mutate
captain state. Its signature has positive/negative type fixtures, but legacy
bodies and save/wire types remain partial. The routing boundary does not provide
full state isolation or complete type coverage.

## Independent baseline

- Untouched source: `680a6f8e696dc7f1eca677ebc52ae795ad3d6593` (cargo PR55).
- `server/game.ts` SHA256 before extraction:
  `79abf046329fdb2d778a2a34e0ca55667234b98be47c8117cc51c976889e7ac6`.
- Fixture source: the baseline `Game` and synthetic fixtures exported by
  `test/message-routing.ts`.
- Reference: `test/fixtures/message-routing-v33.json`. Expected traces are
  committed, not generated by test runs.
- The 79 scenarios record all 56 routes, invoked owners/arguments, call ordering
  and changes to synthetic save/entity/input/mission-target state. Session/save/
  space identities are replaced with markers; no clocks, randomness or production
  saves enter this fixture.
- Additional cases include input/target/rename/abandonment/pause branches,
  unknown/inherited names and replacement of methods/services/spaces after route
  construction. Construction must not read late-initialized dependencies.

The trace test checks **routing**, not correctness of every delegated operation.
Existing feature, real action, persistence, network, fuzz and browser checks remain
necessary. The test separately exercises `Game.onMessage`'s login/freeze/
activity/flood boundaries and is registered in canonical server CI.

## Review checklist

- Compare routing behavior with the independent fixture, including the explicit
  capability receiver (`this`) and operation order.
- Confirm live getters/forwarding preserve reassigned state, service lookup,
  method receiver and operation order.
- Check guide links and entry points against the code.
- Run focused parity, positive/negative contracts, feature characterization and
  the full canonical suite; record actual results in the PR.
- Treat hosted checks as a separate result; local green is not hosted green.

Routing checks do not measure runtime speed or cover every implementation branch.
